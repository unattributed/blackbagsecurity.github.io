<section class="pt-approach-band" aria-label="Engagement and methodology">
  <article aria-labelledby="requirement-title">
    <h2 id="requirement-title">Engagements Built Around the Requirement</h2>
    <p class="pt-panel-lead">White-box, grey-box or black-box testing — selected according to your objective.</p>
    <p>Where source code, architecture, test identities or engineering context are available, we use them when doing so increases assurance. Where the requirement is to understand what an external attacker can discover unaided, we preserve that constraint. Testing can be focused on a release, a particular workflow, a defined environment, a compliance requirement, or a broader security-assurance objective.</p>
  </article>
  <article aria-labelledby="methodology-title">
    <h2 id="methodology-title">Methodology Without Checkbox Testing</h2>
    <p class="pt-panel-lead">Structured where standards help. Adaptive where real systems require it.</p>
    <p>Testing plans can be informed by established guidance such as the OWASP Web Security Testing Guide (WSTG), OWASP API Security, PTES and other engagement-appropriate methodologies, while remaining driven by the actual application, architecture, threat model and client requirements.</p>
  </article>
